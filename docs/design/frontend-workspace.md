## Reading order and hierarchy

The dashboard (`DashboardPage.vue`) is composed with the D1 workspace components for the first time:

1. **Committed context** — the shell context strip (account · valuation date · reporting currency) stays in the fixed app bar, exactly as D2 delivered it. The dashboard does not duplicate it; the values region repeats it as a quiet `workspace-meta` line (`All accounts · 2026-09-08 · USD`, long account names wrap) so the numbers stay attributable while scrolling.
2. **Portfolio values** — `PortfolioMetrics` renders the five actual summary fields as a semantic `<dl>`: dominant **Total NAV** (`--workspace-metric` clamp size, full row) above four quieter equal metrics (Invested, Cash out, Total return · *Since inception*, IRR since inception) in a 4-column grid (2-column below 960px). Values are the backend-formatted strings verbatim — `$100.00`, `($25.00)`, `−2.40%`, `N/R` for null; no parsing, no second currency symbol, zeros and losses never hidden.
3. **Value and return over time** — the incumbent Chart.js NAV card, full width, unchanged props/events (same `update-params` contract, retained rendering while updating). Scoped-only CSS: the frequency `v-btn-toggle` wraps and the canvas height drops 600→360px below 600px. Dense canvas point labels are untouched; they remain a C3 issue.
4. **Allocation** — `WorkspaceSection` with the three incumbent `BreakdownChart` cards side by side at ≥960px (stacked below). **Transitional state:** these are still horizontal bars, not the three solid pies — C4 owns the pies; each card keeps its Chart/Table tabs so the allocation table remains one obvious click away.
5. **Historical reconciliation** — `WorkspaceSection` wrapping the existing `SummaryOverTimeTable` (card chrome removed; table scrolls locally inside `.workspace-table-region`). **Update Account Performance** was reduced from a large primary button inside the card to a secondary tonal action in the section header, hidden while the section is loading/failed.

Page title: `WorkspacePage` renders the single `h1` ("Dashboard"); the shell releases its duplicate heading per the D1 ownership contract.

## Positions pilot integration

## Failures and corrections during the pilot

1. **Browser layout case failed after the dashboard switch** — its long-title check targeted the shell's legacy h1, which the shell correctly no longer renders once the route owns its heading. The check now accepts either heading (`legacy-page-heading` or `workspace-page-heading`); intent (single h1 in main, no fixed-header growth) unchanged.
2. **Mobile sticky Name column covering the viewport** — found in the first mobile positions review, fixed with the narrow-screen cap, re-verified (see above). Positions screenshots retaken after the fix.
3. **`vite preview`/static build path errors on Windows** (rolldown entry resolution with backslash roots; QA script initially served the wrong directory) — fixed inside the throwaway QA script only; no app change.
4. **Positions toolbar controls clipped/off-screen (PR review round)** — my first mobile verification only measured bounding boxes and missed that Vuetify's `.v-toolbar__content` is a fixed inline 64px box with `overflow: hidden`: below 600px only the Year select was really visible, and hit-tests at the Search/Columns/Rows positions returned table cells. The correction makes the toolbar box grow and wrap at every width (`height: auto !important` against the inline style), gives the Columns button a 44px touch target, narrows the Search column basis and makes the Rows column content-sized — the old 12-column basis sum plus the Columns button had also been pushing the Rows-per-page select past the right viewport edge at sm/md widths (1024/720 CSS px included). A rendered regression now runs in the browser `layout` case at all four viewports: each control must be inside the toolbar box, within the viewport, and actually hittable (`elementFromPoint`), and the Columns menu must open with its 20 column entries. Observed RED against the unfixed markup (mobile: clipped Columns button; desktop/tablet/zoom-200: Rows select past the viewport), GREEN after the fix. The committed `qa-native-zoom.mjs` was also rewritten to the documented key-event method (the first committed version used `Emulation.setDeviceMetricsOverride`, which does not reproduce Chrome's zoom devicePixelRatio in this build); it now reaches exactly 200% (dpr 2.0, CSS 720×500) and exits non-zero otherwise, verified live.
5. **Account selector rendered `[object Object]`** (found during the C3 round-3 mobile capture review; fixed separately after C3's integration so the pilot PR stayed bounded) — the browser fixtures supplied `get_account_choices` with `options: []`, so the committed all-selection matched no option and `AccountSelection`'s model fell back to the raw committed object, which Vuetify displayed verbatim. Fix, fixtures, and regressions are recorded in [the account-selector label fallback section](#account-selector-label-fallback-pr).
6. **Layout case's positions-toolbar probe was scroll-dependent (pre-existing, found while gating this fix)** — the probe centered the data table and then measured the toolbar wherever that left it: on tablet/mobile the toolbar landed underneath the fixed header (year select fully inside the header's shadow; covering element the header's own summary span), failing the hit-test. Verified pre-existing: identical failure on pristine `2e77e5c7` and `f6892bf8` (the latter had recorded a green full-suite earlier the same day — the geometry is marginal enough that environment rendering metrics flip it). The probe now centers the toolbar itself with an explicit nudge fully below the fixed header and asserts that clearance as a precondition, so it measures controls users can actually see; hit-testing is unchanged and stricter.

## Account selector label fallback (PR: `codex/account-selector-label-fallback`)

The dashboard header's account select displayed Vuetify's raw `[object Object]` whenever the committed selection matched no loaded option — with the browser fixtures' empty `options: []` this was every page at every viewport, with the committed all-selection.

- **Fix (`AccountSelection.vue`)** — the select renders its display through a `selection` slot fed by the shared `committedAccountLabel` helper (`accountUtils.js`, already the single source for the shell's committed provenance labels): the matching option's title, `All accounts` for the all selection, `Unavailable` for an unmatched specific selection. The model keeps the committed selection unchanged; no option is invented, no repair request is fired, and `handleAccountChange`/arrow-switching behavior is untouched — the raw-object model fallback remains, it just can no longer leak into the display.
- **Backend-faithful fixtures** — `prepare_account_choices` output mirrored exactly (backend/core/user_utils.py): `General`/`All accounts`, `Your Accounts`, `Brokers`, `Account Groups` sections with `__SEPARATOR__` rows and `[name, {type, id, display_name}]` choices — applied to `get_account_choices`, its `longAccount` variant (long display name preserved) and `user_settings_choices.account_choices`. The context-failure flow's extra synthetic account now appends inside the `Your Accounts` section (the backend never emits top-level pairs) with a unique id (9), so the pending-label lookup cannot match a different account with a colliding id.
- **Regressions (RED→GREEN)** — `AccountSelection.label.spec.js` mounts the REAL Vuetify select (`createVuetify` + attachTo body, no label-simplifying stub): all/named-account/broker/group labels, empty choices (fallback `All accounts`), a committed account missing from options (fallback `Unavailable`), delayed option loading (safe label before the reconcile, correct title after, committed selection unchanged), a failed context change (committed label retained, error surfaced, never adopts the failed target), a successful change, and a no-raw-object assertion in every case (also rejecting raw JSON-ish text). RED observed: the three fallback cases failed with the literal `[object Object]` string. The context and layout browser cases now probe the selection-slot element (`.v-select__selection` — the slot replaces Vuetify's `.v-select__selection-text`) and assert that `[object Object]` never renders anywhere on the page at any viewport.
- **Gates (actual exit codes, committed head `29334768`)** — full unit suite 553 tests / 75 files (0) · `type-check` / `type-check:reliability` / `type-check:charts` (0) · lint (0) · build (0) · FULL browser suite 72 profiles (0) including the focused `context` and `layout` cases.
- **Review follow-up: the underlying input value leaked too (reproduced, then fixed)** — with the selection slot in place the VISIBLE label was safe, but the reviewer suspected Vuetify still exposes `[object Object]` through the combobox input's `value` for an unmatched committed selection. Gates on committed head `b56b1afc` (exit codes): full unit 553/75 (0), type-checks x3 (0), lint (0), build (0), full browser suite 72 profiles (0). - **Boundaries** — `ProfileSettings.vue` still silently falls back to the all selection (`matchingAccount?.value || { type: 'all', id: null }`) when the committed default account is missing from its choices: a distinct settings-form defect (silent semantic change, not a display leak), deliberately left untouched here. ## Profile Settings account-selection preservation (PR: `codex/settings-account-selection-preservation`)

The settings-form sibling of the header fix above: `ProfileSettings.loadData` replaced a saved account identity that was absent from the returned choices with `{type: 'all', id: null}` (`matchingAccount?.value || { type: 'all', id: null }`), so saving any unrelated preference silently broadened the portfolio scope to All accounts — a silent semantic change, not a display leak, exactly as the boundary note in the header-fallback section predicted.

- **Fix (`ProfileSettings.vue` only)** — the settings response is the form's authority: the identity `{type: selected_account_type, id: selected_account_id}` is preserved exactly when structurally valid (all with a null id, or account/broker/group with a positive integer id — the shapes the backend serializer and context store accept), whether or not choices contain it; a malformed/missing identity resolves to null, never to All accounts, and the live header selection is never substituted. The select's display model is a separate computed: the matched option's own value while resolved, otherwise the safe label string from the shared `committedAccountLabel` helper (`All accounts` for a valid all selection, `Unavailable` otherwise), so neither the visible selection nor the underlying input value can render `[object Object]`. Selections are accepted only from actual selectable option values; the safe display string can never enter the form identity or a transport payload. Unresolved states show a persistent field message ("Your saved account selection is unavailable. Choose an available account selection before saving."; "Account choices are unavailable. Reload settings before saving." when the response contains no matching option — even a valid all identity stays unresolved then). Save is disabled and `saveSettings` guards before the first write until settings and choices have loaded successfully and the identity matches a real selectable option; a `saving` lock blocks duplicate submissions while the existing two-stage save (profile write, then the committed-context queue) is in flight. Rejections surface honestly: a rejected profile write never reaches the context queue, a rejected context write shows the error without a success message, and the chosen identity plus all other edits are retained in both cases. Existing save order, payload shapes and queue ownership are untouched; no auto-save when options arrive; no new API.
- **Unit regressions (RED→GREEN, real Vuetify mount)** — `ProfileSettings.accountSelection.spec.js` (14 cases): matching all/named/broker/group identities with saving enabled; a saved identity missing from choices kept exactly (visible label AND input value `Unavailable`, the exact message, Save disabled, only the five real options in the menu, the store's deliberately different committed selection never adopted); empty choices with a valid all identity (honest `All accounts` label, still unresolved); malformed and missing identities never defaulting to All accounts; delayed load (spinner, no form, then response authority); load failure (saving blocked, handler produces zero writes); unresolved submissions through a dispatched form submit AND the direct handler (zero writes, unrelated edits preserved); explicit account and All accounts selections saved with exact payload shapes (context-owned fields absent from the profile write, original type/id through `changeContext`); the safe display string and a non-selectable identity rejected as selections; duplicate submissions while pending (exactly one profile write and one context call); a rejected profile write (field errors, no context writes, retained edits and selection, corrected retry) and a rejected context write (error without success, one attempt each, retained selection, Save re-enabled after the sequence). RED observed against the base `3f3cad9e`: 12 of the 14 failed, including the saved identity silently becoming `{type: 'all', id: null}`; the pending-duplicate case was RED against the Task-1 head and green after the saving lock. `ProfileSettings.context.spec.js` fixtures now provide backend-faithful available choices so its injected broker identity is really selectable; its queue/payload assertions are retained unchanged.
- **Rendered regression (new `settings-account` browser case)** — desktop full flow plus a 390px pass over a bounded `settingsAccountFlow` fixture mode (saved account 42 absent from the choices; the saved selection changes only after a confirmed account POST, so save readbacks behave like the real backend; queueable one-shot profile/context rejections): unavailable state with exact visible label, exact input value and persistent message; zero mutation POSTs after a disabled-button click and a dispatched form submit; a held-choices delayed initial load (spinner, no form, then the same honesty); native 200% zoom via dpr-verified CDP key events with visible, hittable controls and message (the disabled Save is correctly inert through Vuetify's `pointer-events: none` — distinguished from real occlusion in the probe); keyboard resolution (open, ArrowDown, Enter, a real option, no writes); explicit Second-account and All-accounts selections saved through the existing queue with exact recorded payloads and dashboard readbacks of both saved selections (the profile page hides the header context strip by design, so the committed label is verified where it renders); rejected profile and context writes with honest errors, no extra writes, retained edits and successful retries; a final page-error sweep. 390px: the saved identity is reset server-side and the same unavailable assertions and zero-write guarantee are checked. - **Transitional allocation bars:** the three cards still render horizontal Chart.js bars. The required final presentation is three solid pies with backend-ratio labels — that is mandatory C4 work and is **not** satisfied by this pilot.

- **Table controls remain incumbent:** grouped presets, organized column chooser, aria-sort and pinned-identity-by-key are **D4**; this pilot deliberately changed none of that behavior (the sticky-width cap is a defect fix, not a redesign).

- **`SummaryCard`** is retained unchanged (with its tests) as a compatibility adapter; no view consumes it now. Deleting it is cleanup for a later task.
- **Native zoom via CDP key events:** agent-browser's `press Control+=` does not trigger browser zoom in this headless build; the committed `scripts/qa-native-zoom.mjs` drives `Input.dispatchKeyEvent` (Ctrl+0 reset, then Ctrl+Plus steps) and self-verifies `devicePixelRatio` so the documented evidence is reproducible from the repository.

## PR #51 review round (2 October 2026)
